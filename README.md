# Cache Performance Lab — PostgreSQL + Redis на Go

Практический проект на Go, который показывает, **зачем приложению нужен кэш и насколько он может ускорить получение данных**.

Проект позволяет на реальном HTTP API сравнить два сценария:

* **Cold Cache** — данные отсутствуют в Redis и загружаются из PostgreSQL.
* **Hot Cache** — данные уже находятся в Redis и возвращаются из памяти.

В результате можно не просто прочитать о кэшировании, а **самостоятельно запустить систему, выполнить запросы и увидеть разницу в latency**.

## Что можно получить из этого проекта

Проект будет полезен разработчикам, которые хотят:

* понять принцип работы **Cache-Aside Pattern**;
* увидеть взаимодействие **Go → Redis → PostgreSQL**;
* разобраться, чем отличается обращение к данным в RAM от обращения к базе данных;
* посмотреть, как реализуется **прогрев кэша (Cache Warm-up)**;
* научиться измерять latency HTTP-запросов;
* получить готовый пример инфраструктуры с **Docker Compose**;
* использовать проект как основу для собственных экспериментов с кэшированием.

## Как работает система

При запросе к продукту приложение сначала проверяет Redis.

```text
HTTP Request
     │
     ▼
   Go API
     │
     ▼
   Redis ──────► Cache HIT ──────► Response
     │
     │ Cache MISS
     ▼
 PostgreSQL
     │
     ▼
  Redis
     │
     ▼
 Response
```

### Cache HIT — горячий кэш

Если данные уже есть в Redis, приложение получает их из памяти и возвращает клиенту.

### Cache MISS — холодный кэш

Если данных в Redis нет, приложение обращается к PostgreSQL, получает данные и сохраняет их в Redis для последующих запросов.

Таким образом, один и тот же endpoint позволяет увидеть разницу между обращением к базе и обращением к кэшу.

## Демонстрация производительности

В проекте предусмотрена имитация более медленного обращения к базе данных с задержкой около 500 мс.

Пример измерений:

| Сценарий | Источник   |    Время |
| -------- | ---------- | -------: |
| Cold     | PostgreSQL |  ~503 мс |
| Hot      | Redis      | ~0,18 мс |

В приведённом эксперименте запрос из Redis выполнялся примерно **в 2700 раз быстрее**, чем запрос из PostgreSQL.

> Фактические значения latency зависят от окружения и нагрузки. Цель эксперимента — показать принципиальную разницу между обращением к постоянному хранилищу и данным, находящимся в памяти.

## HTTP API

Получить продукт можно через endpoint:

```text
GET http://localhost:8080/product/{id}
```

Например:

```text
http://localhost:8080/product/1
```

Ответ содержит данные продукта, состояние кэша и время выполнения запроса:

```json
{
  "data": {
    "id": 1,
    "name": "Product 1",
    "price": 435.37
  },
  "status": "HOT",
  "time": "562.908µs"
}
```

Если продукта нет в Redis:

```json
{
  "data": {
    "id": 50,
    "name": "Product 50",
    "price": 120.30
  },
  "status": "COLD",
  "time": "502.455967ms"
}
```

Это позволяет непосредственно увидеть, **откуда были получены данные и сколько занял запрос**.

## Прогрев кэша

При запуске приложения предусмотрен механизм **Cache Warm-up** — предварительное заполнение Redis популярными данными.

Это позволяет уменьшить количество первых запросов, которые должны обращаться непосредственно к PostgreSQL.

Механизм полезен для понимания сценариев, когда после запуска приложения кэш необходимо заранее наполнить часто используемыми данными.

## Технологии

* **Go 1.21+** — HTTP API и бизнес-логика;
* **PostgreSQL 15** — основное хранилище данных;
* **Redis 7** — in-memory cache;
* **Docker Compose** — запуск инфраструктуры;
* **Cache-Aside** — стратегия взаимодействия приложения с кэшем и БД.

## Быстрый запуск

### 1. Запустить PostgreSQL и Redis

```bash
docker-compose up -d
```

### 2. Инициализировать базу данных

```bash
docker exec -i $(docker ps -qf "name=postgres") \
  psql -U user -d inventory < scripts/init.sql
```

### 3. Запустить Go-приложение

```bash
go run main.go
```

### 4. Выполнить запрос

```text
http://localhost:8080/product/1
```

Повторите запрос несколько раз и сравните полученные значения `status` и `time`.

Также можно запросить продукт, которого ещё нет в кэше:

```text
http://localhost:8080/product/50
```

Первый запрос продемонстрирует сценарий **Cold Cache**, после которого данные будут помещены в Redis. Последующие запросы позволяют наблюдать работу **Hot Cache**.

## Что можно изучить на практике

Проект можно использовать как небольшую лабораторию для экспериментов:

1. Очистить Redis и выполнить запрос.
2. Посмотреть время получения данных из PostgreSQL.
3. Повторить тот же запрос.
4. Сравнить latency после появления данных в Redis.
5. Проверить работу автоматического прогрева.
6. Изменить задержки и параметры кэширования.
7. Поэкспериментировать с объёмом данных и нагрузкой.

Так проект помогает перейти от теории к практическому пониманию вопроса:

**«Что происходит с производительностью приложения, когда часто запрашиваемые данные находятся в кэше?»**

## Идея проекта

Это не production-ready cache layer, а **практический стенд для изучения кэширования и измерения его влияния на производительность**.

Главная ценность проекта — возможность увидеть весь путь данных:

**PostgreSQL → Redis → Go API → HTTP Client**

и на конкретных измерениях понять, почему кэширование часто становится важной частью backend-архитектуры.
